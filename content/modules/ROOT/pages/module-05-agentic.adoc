= System Administration with Agentic AI

In the last module, you stepped into the developer role building applications using private LLM endpoints. Now, you'll become a **site reliability engineer (SRE) or DevOps practitioner** focused on observability, diagnostics, and operational scale.

But you won't go at it alone, you'll work with agentic AI tooling to navigate your OpenShift environment in real time - just like a modern SRE team building insight-driven automation.

NOTE: You're still using the **same Nemotron model** from the MaaS deployment you accessed in earlier modules. The difference? Instead of consuming it through the VS Code Chat interface, you'll now interact with it through the Gen AI Studio Playground with MCP server integrations for infrastructure operations. You can use other clients that integrate with MCP, including coding harnesses like VS Code Chat, but we're just going to use the playground for this section to get familiar with it. This demonstrates how a single, centrally-managed model serves multiple personas and use cases across your organization.

== Why Agentic AI for Admins?

Think of agentic AI as your copilot for cluster operations - ready to answer complex infrastructure questions using reasoning and real-time data.

Instead of navigating complex dashboards, YAML, and shell scripts, you'll try something new:

* “What’s consuming the most memory in our dev cluster right now?”

* “Were there any pod crashes in the last 30 minutes?”

* “Why did that Job fail this morning?”

These natural-language prompts get translated into real queries and results. The outcome? Faster issue resolution, increased system transparency, and lower barrier to operational insights for both technical and non-technical users.

That's an example of the power of agentic AI.

== Meet Your New Toolkit

In this module, we'll use a preconfigured stack that includes:

* **Gen AI Studio Playground** - an integrated UI feature in Red Hat AI for testing model responses, MCP server integrations, and tool invocations before exporting agents as production code. Use it to validate that models, prompts, and external connections work together correctly, then export the validated configuration to your application.

* **Kubernetes MCP Server** - allows our LLM agent to interact with our live OpenShift cluster and deployed resources. OpenShift includes support for a variant of this MCP server, and OpenShift AI can manage its lifecycle for you from a trusted catalog, but we're not exploring these interfaces in the lab today.

* **Rocket.Chat MCP Server** - allows our LLM agent to interact with a Rocket.Chat workspace. We will use it to interact with a specific Rocket.Chat workspace as a stand-in for your organization's own chat platform, whatever it may be.

* **NVIDIA Nemotron 3 Nano 30B A3B FP8 Model** - a lightweight, instruction-tuned model optimized for agentic workflows and tool calling. This model drives the agent's decision-making as it translates natural language into MCP server tool invocations.

IMPORTANT: This agent will have real access to the OpenShift cluster and Rocket.Chat workspace you're sharing with everybody else in this lab. The MCP integration is read-only, but it is cluster-wide. The Rocket.Chat workspace is shared with everyone in the lab, agentically and otherwise. When experimenting:

* Be courteous and kind
* Do not add information that you do not want everyone else to have access to
* Do not attempt to break out of the sandbox we've dropped you into
    * There's nothing particularly valuable in this ephemeral environment you could get access to even if you succeed
    * Attempting to will just disrupt the experience for everyone else

=== Using the playground

This is where the magic happens. The playground lets you test-drive your entire agentic AI stack - model, prompts, MCP servers, and even vector data for RAG - **before writing a single line of application code**.

Think of it as your **sandbox for engineering agents**. Instead of deploying blind and debugging in production, you validate the whole chain here:

* Does the model understand my prompts correctly?
* Are the MCP servers responding with the right data?
* Does the combination of model, prompts, and tools behave correctly in the context I need the final agent to?

**The workflow:** Experiment here → validate behavior → export configuration → deploy applications with the agentic workflow baked in, behind an industry-standard OpenAI Responses API.

In the playground, you'll see a chat interface with your model preselected and a default system prompt. You can adjust the system prompt or temperature as needed.

[.bordershadow]
image::gen-ai-playground.png[]

NOTE: The **temperature** setting controls model creativity. Keep it **low** (0.0-0.3) for deterministic, accurate responses - the kind of behavior you probably want when querying infrastructure. Higher temperatures introduce randomness, which can break tool calls, but might be useful for debugging or design work.

Click on the "MCP" tab to view MCP servers

See what you have available, then click the checkbox to select the "Kubernetes-MCP-Server" and click "Save" to enable all of the Kubernetes tools.

NOTE: Authorization to the MCP servers is **session-based**. If you refresh or reopen the playground, you might need to re-select the MCP servers and reconfigure your settings. Your permissions are granted to these servers by your log-in to the Dashboard and Playground.

Your agent is now live and connected to both Kubernetes and Rocket.Chat. You can issue natural language commands and watch them translate into real infrastructure operations.

Notice the warning shown by the Playground here:

[.bordershadow]
image::gen-ai-playground-tool-warning.png[]

NOTE: Depending on what model you're using, you might start to experience a condition called "tool confusion" with too many tools and a model that's not built to handle it. This decision paralysis might manifest as reasoning loops arguing about the right tool to pick, or it might simply pick the wrong one more often than it should.

To optimize performance and help the model focus on the most relevant operations, we'll deselect some of the less frequently used tools. This improves response accuracy and reduces the amount of reasoning required to complete tasks. Some models might do well with more tools, but here we're using a "Nano" model variant, so we'll help it out a bit.

== Investigate our OpenShift Resources

Keep in mind that you might need to utilize the right keywords so that you're engaging with the appropriate tools, so here are some prompts we've seen work correctly without much fine-tuning on the system prompt.

In the chat, enter:

[source]
----
List all pods in the redhat-ods-monitoring namespace.
----

Response output will vary slightly, but you should see it correctly list the active pods in the `redhat-ods-monitoring` namespace (which the MCP server has access to, even though you don't). The pods listed are part of the OpenShift AI observability stack and handle collecting, storing, querying, and displaying dashboards for AI workloads like the model we're talking to right now.

✓ **Success indicator**: You should see output listing several pods with names like with `data-science-perses-0` and `prometheus-data-science-monitoringstack-0`. The agent may or may not give you more details, like pod health or ready container count.

Let's try something else:

[source]
----
Get the last few lines of logs from the only running Pod in the llm namespace.
----

✓ **Success indicator**: You should see log output including timestamps. The logs are from the very vLLM instance that's serving your requests for this lab! You can probably see how busy it is processing requests for everyone right now.

Feel free to experiment further with the tools available before moving to the next step.

=== Post a Message to our Rocket.Chat Workspace

With our Rocket.Chat MCP Server, we can extend our agentic AI experience beyond Kubernetes and into team collaboration tools (among many other possibilities).

This MCP server bridges your NVIDIA Nemotron model with a Rocket.Chat workspace to fetch and post messages, even those related to context it gathered from our other tools.

Open the link:{rocketchat_url}[Rocket.Chat application,window=_blank] and log in with the following credentials:

**User**:

[source,subs=attributes+]
----
{user}
----

**Password**:

[source,subs=attributes+]
----
{password}
----

NOTE: The Rocket.Chat workspace is pre-configured with a `#workshop` channel where your AI agents will post messages. You will observe the messages there after sending them through the playground.

**Why this matters:**

* SREs and DevOps teams often work across multiple collaboration channels.

* By giving your AI visibility into a collaboration space like Rocket.Chat (similar to Slack), you can use natural language to check team communication spaces or to post information without switching tools.

* This is a safe, controlled example — you can read channels and post messages through your authorized bot user.

==== In the Gen AI Studio Playground chat interface, type:

[source]
----
List all Rocket.Chat channels in our workspace.
----

✓ **Success indicator**: You should see a list of available channels including `#general` and `#workshop`.

Now, let's post a message to our Rocket.Chat workspace:

[source]
----
Post a message to the #workshop channel: "Hi from {user}".
----

Go check the `#workshop` channel in the Rocket.Chat application to see your message.

==== ChatOps debugging of problem applications

Now, let's try out a real use case for this! Our playground is just the kind of place we'd want to validate our prompts and tool behavior for an agentic. In a production environment, you would likely use a more robust automation to send logs or other information from your Red Hat AI cluster to Rocket.Chat, but the Playground will help you get the feel.

We have an example app deployed to the `demo` namespace. This application is a simple polling monitor application for another notional application in your infrastructure, just doing a health check for that external application. Your OpenShift cluster's AlertManager warned you that there was a problem with your health check pod, but it didn't tell you why. Let's use your prototype agent harness in the Playground to figure out what's gone wrong with it.

[source]
----
Get the Pod logs for the demo-app Deployment in the demo Namespace. Review the logs for any errors or warnings, then investigate any issues found and post a diagnosis to the #workshop channel in Rocket.Chat. Preface the message with the marker `**{user}**` so I can find it.
----

== Summary: What You Did

* **Integrated the centralized LLM with a tool-using agent in the Playground** - connecting NVIDIA Nemotron with MCP servers for live infrastructure interaction
* **Explored OpenShift resources with natural language** - querying pods, namespaces, and logs without writing kubectl commands

**Why This Matters:**

This agentic pattern enables on-call engineers and SREs to query infrastructure using conversational language, reducing context switching and accelerating incident response. **Real-World Applications:**

* **Automated incident response**: Query cluster health, retrieve logs, and post findings to Slack/Teams without leaving your chat window or agent harness

* **Proactive monitoring**: Agents can watch for specific patterns and automatically notify teams when issues arise

You just used AI to reduce operational complexity and speed up workflows - imagine scaling this across your entire infrastructure stack!
